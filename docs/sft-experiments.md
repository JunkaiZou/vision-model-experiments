# SFT 实验详解（Exp1-6）

## 微调框架概述

使用 **Swift** 框架对 Qwen3-VL 4B 进行有效的参数微调（LoRA）。

### 训练基础设置（所有实验通用）

| 配置项 | 数值 |
|--------|------|
| 基础模型 | Qwen3-VL 4B Instruct |
| 微调方法 | LoRA (Low-Rank Adaptation) |
| LoRA Rank | 8 |
| LoRA Alpha | 32 |
| 目标模块 | 所有线性层 (all-linear) |
| 精度 | bfloat16 |
| 注意力实现 | flash_attn |
| 分布式策略 | ZeRO-2 |
| 梯度检查点 | 启用 |
| VIT 冻结 | 是 |
| Aligner 冻结 | 是 |

### SFT 数据集构建

所有实验共同的数据准备流程：

**步骤 1：数据收集**
- 四个数据集的训练集部分
- ICDAR2015, ICDAR2017MLT, MSRA-TD500, RCTW-17
- 总计 ~14,500 个样本

**步骤 2：格式标准化**
- 所有 GT polygon 转换为 AABB（axis-aligned bounding box）
- 坐标归一化到 [0, 1000] 范围
- 坐标按中心点位置 (y, x) 升序排列（保证可复现）

**步骤 3：JSONL 格式构建**
```json
{
  "messages": [
    {
      "role": "user",
      "content": "<image>Detect all text regions... [提示词]"
    },
    {
      "role": "assistant",
      "content": "[{\"bbox_2d\": [...]}, ...]"
    }
  ],
  "images": ["ICDAR2015/images/img_1.jpg"]
}
```

## 实验 1（Baseline）：LoRA + ZeRO-2, 1 Epoch

### 参数配置

| 参数 | 值 |
|------|-----|
| Epochs | 1 |
| Per-device batch size | 1 |
| Gradient accumulation | 2 |
| Max sequence length | 4096 |
| Packing | 启用 |
| Padding free | 启用 |
| Learning rate | 1e-4 |
| Warmup steps | 50 |

### 关键观察

**梯度范数曲线分析**：

| 实验组 | 特征 | 含义 |
|--------|------|------|
| none | 梯度最大、波动剧烈 | 无先验提示，模型优化困难 |
| center/random/text | 梯度稳定、无异常值 | 先验信息降低了优化难度 |
| **text** | **梯度最小（0.27）** | **训练最稳定** |

**Loss 曲线特征**：

- **none 组**：最终 loss = 0.438（最高）
- **center 组**：最终 loss = 0.396（最低）✅
- **random 组**：最终 loss = 0.406
- **text 组**：最终 loss = 0.434（次高）

**Exp1 结论**：
- ✅ 先验信息确实降低了训练难度
- ⚠️ text 组 loss 较高，可能因为 max_length 截断导致 prompt 不完整
- ❓ 需要进一步实验验证

## 实验 2（Max Length 调整）：针对 text 组优化

### 问题诊断

Exp1 中 text 组表现不佳的原因：

**假设**：max_length=4096 太短，导致长 prompt 被截断

**数据**：
- 平均输入 token 长度：3998.67
- 最小值：3641
- 最大值：4096 ✅（已达到上限）

结论：很多样本的 prompt 被截断了。

### 参数调整

```yaml
max_length: 4096 → 8192  # 翻倍
packing: true → false    # 禁用 packing（与可变长 flash_attn 冲突）
padding_free: true → false
```

### 结果

| 指标 | 4096 | 8192 | 改进 |
|------|------|------|------|
| eval_loss | 0.43386 | 0.42414 | -0.0097 |
| token_acc | 0.83048 | 0.83137 | +0.00089 |
| 训练时长 | 10m 55s | 20m 56s | +92% |
| 显存占用 | 25.23 GB | 27.86 GB | +2.63 GB |

**Exp2 结论**：
- ❌ max_length 不是 text 组表现差的原因
- ❌ 增加到 8192 带来的改进微乎其微，反而增加成本
- ✅ 结论：回退到 max_length=4096

## 实验 4（Text 组消融）：诊断和优化

### 假设与测试

**假设 1**：数量截断帮助性能
```
text vs text_20：两者几乎无差异 ❌
```

**假设 2**：输入输出格式对齐很关键
```
text_cosis（按中心点排序对齐）vs text（原始顺序）
结果：text_cosis 显著优于 text ✅
```

**假设 3**：输出格式规范化帮助学习
```
text_bc（输出 {"bbox": ..., "content": ...}）vs text_cosis
结果：text_cosis 优于 text_bc ✅（但差异较小）
```

### 实验 4 的最优配置：text_cosis

关键变化：
1. **输入顺序对齐**：Prompt 中的文本顺序与 GT 框顺序保持一致
2. **数量对齐**：Prompt 中列出的文本数与 GT 框数相同
3. **只列可识别文本**：跳过 illegible 和空文本

### 效果

| 数据集 | text_cosis | baseline | 改进 |
|--------|-----------|----------|------|
| ICDAR2015 | 86.5% | 83.1% | +3.4% |
| ICDAR2017MLT | 74.2% | 71.3% | +2.9% |

**Exp4 结论**：
- ✅ 输入输出的顺序和数量对齐很关键
- ✅ text_cosis 现在优于 center 组
- ❌ 多轮推理（逐文本循环）：成本高但收益低

## 实验 5（8 点多边形）：处理倾斜文本

### 问题背景

4 点 AABB（矩形）无法准确表示**倾斜文本**：
- 细长且倾斜的文本框
- IoU 计算时，外接矩形面积过大
- 导致大量误判

### 改进方案

从 4 点坐标（矩形）升级到 8 点坐标（多边形）：
```
4点：[xmin, ymin, xmax, ymax]
8点：[x1, y1, x2, y2, x3, y3, x4, y4]  # 四个顶点
```

### 结果对比

**ICDAR2015 上的表现**：

| 指标 | 4点 (text_cosis) | 8点 (text_cosis_8) | 改进 |
|------|-----------------|-------------------|------|
| Precision | 88.7% | 89.4% | +0.7% |
| Recall | 85.2% | 87.1% | +1.9% |
| Hmean | 86.9% | 88.2% | +1.3% |

**细长倾斜框的改进**：
- 明显缓解了之前的 IoU 偏低问题
- 倾斜文本的检出率提升

### 显存和时间成本

| 指标 | 4点 | 8点 | 增长 |
|------|-----|-----|------|
| 平均推理时间 | 135ms | 160ms | +18.5% |
| 单题最大 tokens | 2048 | 4096 | +100% |

**Exp5 结论**：
- ✅ 8 点格式显著改善倾斜文本的检测
- ⚠️ 输出 token 数翻倍，极端样本可能被截断
- ✅ 整体上性能收益大于成本

## 实验 6（自定义 Token）：压缩坐标表示

### 背景

Exp5 中，8 点输出导致极端样本（100+ GT 框）被截断。

### 解决方案

定义特殊 token `<C0>` 到 `<C1000>` 表示坐标值：
```
原来：[673, 254, 816, 254, 816, 280, 673, 280]
现在：<C673> <C254> <C816> <C254> <C816> <C280> <C673> <C280>
```

预期：输出 token 从 8 个数字 → 8 个特殊 token（可能更紧凑）

### 实验配置

三个变体：
- **sft_text_cosis_8_tok**：仅 LoRA + 新 token
- **sft_text_cosis_8_tok_embed**：解冻 embedding 层 + 新 token
- **sft_text_cosis_8_tok_embed_lmhead**：解冻 embedding + lm_head

### 结果

| 变体 | 训练成功 | 性能 | 备注 |
|------|---------|------|------|
| _tok | ❌ | loss > 1.4 | 模型没学会新 token |
| _tok_embed | ❌ | loss > 1.0 | 略有好转但仍失败 |
| _tok_embed_lmhead | ✅ | loss ~0.38 | 成功，性能与 8 点相近 |

### 最终结论

- ✅ 自定义 token 可以节省输出长度
- ⚠️ 需要解冻更多参数才能有效学习
- ❌ 性能与标准 8 点格式相当，增加了复杂性
- 建议：暂时放弃自定义 token 方案，继续用标准 8 点格式

**最终推荐的微调方案**：

| 方面 | 选择 |

## 经验总结

### Prompt Engineering vs SFT

| 维度 | Prompt-Only | SFT |
|------|------------|-----|
| 性能 | 79.2% | 88.2% |
| 可调整性 | 高 | 中 |
| 训练成本 | 0 | 高 |
| 稳定性 | 中 | 高 |

### 关键洞察

1. **先验信息很关键** — 无论是 Prompt-Only 还是 SFT，都能显著改善性能
2. **输入输出对齐重要** — 让 LLM 学习到一致的映射关系
3. **格式规范化有帮助** — 多边形优于矩形，特别是倾斜文本
4. **避免复杂化** — 自定义 token 方案虽然理论上优雅，但实际收益有限

### 可迁移的方法论

这套实验方法论适用于任何 VLM 微调任务：

1. **建立 baseline**（无先验）
2. **消融不同先验**（Exp 1-4）
3. **优化输出格式**（Exp 5）
4. **探索压缩方案**（Exp 6）
